# GigaChat 3 Ultra: пилот, полный эксперимент и сравнение с Lite

## Конфигурация и воспроизводимость

Эксперименты выполнены 11 ноября 2026 года для репозитория Multiagent_LLM_Coordination, ветка `sandbox-integrity`, коммит `5e469e9cfcb185ae9650136dc5c539a9dad50256`. Рабочее дерево содержало незакоммиченные изменения; это не чистый коммит. Все 19 Python-файлов текущего проекта побайтово совпали со снимком Lite в `$ORIGINAL_WORKSPACE\lite-benchmark-work`, а хеши шести файлов протокола и sandbox совпали с Lite-манифестом и обоими Ultra-манифестами. Задачи, промпты, код координации, метрики и реализация sandbox не менялись.

Протокол v2; шесть архитектур, девять задач, по одному повтору. `max_iterations=3`, seed не контролируется, параметры генерации — значения провайдера по умолчанию. Python 3.14.4, Windows, SDK gigachat 0.2.1; Docker Linux, образ `python:3.12.8-alpine3.20@sha256:3b1df87fc50e7d47762aeb48673736079aa22e7c98c8851f5453dd49fc03ad1b`. Порог sandbox — 5 секунд на выполнение кандидата. Preflight: 39 из 39 автономных и Docker-тестов прошли, включая adversarial RPC-тесты. Это не доказывает безопасность: известное ограничение целостности RPC при намеренно злонамеренном кандидате сохраняется.

Старый адрес SDK по умолчанию вернул список без Ultra; на официальном адресе `https://api.giga.chat/v1` та же учётная запись получила список с `GigaChat-3-Ultra`. Для Ultra адрес выбран переменной `GIGACHAT_BASE_URL` без изменения исходников. Lite использовал прежний адрес; различие endpoint — дополнительное ограничение сравнения. Официальная документация указывает новый адрес и идентификатор Ultra: https://developers.sber.ru/docs/ru/gigachat/models/gigachat-3-ultra . Пилот и полный прогон успешно получили ответы по запрошенному идентификатору `GigaChat-3-Ultra`. Бенчмарк не сохраняет поле модели из ответа провайдера, поэтому независимо подтвердить разрешённую сервером модель для каждого вызова нельзя.

Для контроля порога 300 000 токенов полный прогон запущен через внешний `$ORIGINAL_WORKSPACE\ultra-budget-runner.py`: он выполняет неизменённый `main.py`, записывает статистику каждого ответа и останавливает дальнейшие запросы при превышении порога или отсутствии/несогласованности usage. Один вызов способен пересечь порог, поскольку точный расход известен после ответа; фактический расход оставался значительно ниже. Журнал: `$ORIGINAL_WORKSPACE\ultra-full-usage-monitor.csv`.

## Сравнение по задачам

В таблице число успешных архитектур из шести. Сравнение выполняется для одинаковых пар задача–архитектура: **25 пар Lite не прошли, а Ultra прошли; обратных пар нет**.

| Задача | Lite | Ultra | Архитектуры, улучшившие результат с Lite до Ultra |
|---|---:|---:|---|
| t01 normalize_email | 5/6 | 6/6 | centralized |
| t02 parse_csv_line | 0/6 | 6/6 | все шесть |
| t03 merge_intervals | 4/6 | 6/6 | centralized, fully_connected |
| t04 calculate_cart_total | 1/6 | 6/6 | single_agent, chain, feedback_graph, fully_connected, parallel_consensus |
| t05 top_k_frequent | 5/6 | 6/6 | centralized |
| t06 detect_cycle | 5/6 | 6/6 | single_agent |
| t07 analyze_logs | 0/6 | 3/6 | single_agent, chain, parallel_consensus |
| t08 group_by_category | 6/6 | 6/6 | нет различий |
| t09 resolve_build_order | 0/6 | 6/6 | все шесть |

Все три ошибки Ultra пришлись на t07. Просмотр итогового кода показывает конкретные расхождения: `centralized` возвращает в `by_level` уровни с нулевыми значениями, тогда как пустой случай ожидает пустой словарь; `feedback_graph` и `fully_connected` увеличивают `errors` для некорректных строк, а тесты ожидают число корректных записей уровня ERROR. Это наблюдения по коду, а не доказательство внутренней причины поведения модели. Промпт называет поле `number_of_error_lines`, что может допускать неоднозначную интерпретацию. Исходные задачи и тесты не изменялись.

## Исследовательский вывод и ограничения

В этом единственном запуске Ultra `single_agent` уже достигает 9/9. Ни одна координационная архитектура не улучшила этот результат; две сравнялись, три показали 8/9, при расходе от 4,78 до 11,63 раза больше токенов на успех. У Lite некоторые архитектуры получили 5/9 против 4/9 у single_agent, но centralized получил 3/9. Это наблюдение совместимо с гипотезой о снижении пользы координации при более сильной модели на данных задачах, но не доказывает её: одна выборка из девяти задач, один повтор, отсутствие фиксированного seed, потолочный эффект 9/9, различающиеся endpoint и случайная генерация не позволяют сделать статистически надёжный или причинный вывод. Нет оценки вариации между повторами. Рекомендуются заранее запланированные повторения, дополнительные задачи с достаточной сложностью, контроль доступа и endpoint, а также сохранение идентификатора модели из ответа API. Отдельно исследовать неоднозначность t07 и известную RPC-уязвимость до использования недоверенных кандидатов.
